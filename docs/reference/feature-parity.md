# Feature parity: CLI, TUI, VS Code, JetBrains

Every capability starts in the CLI. The TUI (`smith` in a terminal), the VS Code extension and the JetBrains plugin offer the same function in their own medium. "Terminal" means the surface opens `smith` in an integrated terminal, so it has the TUI's behaviour. A dash means the surface has no such function, and the cell says why.

The JetBrains plugin compiles, passes ktlint and its unit tests (the mappers, the algorithms and every flow) in CI. Its dialogs, notifications and tool window were never run in a real IDE, so a JetBrains cell that says "not run in a real IDE" describes what the code does, not what a person saw. Every flow is written against three small ports (run smith, ask, tell), so the flows have unit tests with a fake smith and a fake person. The plugin does not hold `smith serve` open (the VS Code extension does): every flow runs the installed smith (ADR 0025) in a background task and prints in the Output tab. Its Run, Cache and Look Up commands print in the Output tab.

## Rules

- The `--commit` box is unticked in every surface. smith commits only when asked, or when `commit_operations = true` is set.
- The undo hint appears only for a committed change. Otherwise the surface says "Not committed: review with git status".
- A check that lives in the CLI (the npm scope of `smith config set workspace.scope`, a plugin list) reaches every surface at once.
- `smith plugin disable` stops when projects use the plugin, and `--force` goes on. The TUI toggle is reversible, so it shows the count in its note instead of asking.
- The "did you mean" text of the CLI has no surface of its own: each surface lists the valid values in a pick list.
- JetBrains has no gradle build in the development environment of this change: the cells marked "unbuilt" are written and have unit tests for the pure parts, but nobody compiled them. The JetBrains gaps left are swap, derive, divergences, `--like`, why for a setting, try and bootstrap.
