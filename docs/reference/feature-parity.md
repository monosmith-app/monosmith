# Feature parity: CLI, TUI, VS Code, JetBrains

Every capability starts in the CLI. The TUI (`smith` in a terminal), the VS Code extension and the JetBrains plugin offer the same function in their own medium. "Terminal" means the surface opens `smith` in an integrated terminal, so it has the TUI's behaviour. A dash means the surface has no such function yet.

## Rules

- The `--commit` box is unticked in every surface. smith commits only when asked, or when `commit_operations = true` is set.
- The undo hint appears only for a committed change. Otherwise the surface says "Not committed: review with git status".
- A check that lives in the CLI (the npm scope of `smith config set workspace.scope`, a plugin list) reaches every surface at once.
- `smith plugin disable` stops when projects use the plugin, and `--force` goes on. The TUI toggle is reversible, so it shows the count in its note instead of asking.
- The "did you mean" text of the CLI has no surface of its own: each surface lists the valid values in a pick list.
- JetBrains has no gradle build in the development environment of this change: the cells marked "unbuilt" are written and have unit tests for the pure parts, but nobody compiled them. The JetBrains gaps left are swap, derive, divergences, `--like`, why for a setting, try and bootstrap.
| One pick per single-choice axis (framework, shell, host, trigger, runtime) | the solver refuses two choices on one axis unless both are `many` | a tick on a second choice of the axis unticks the first, with a one-line note; additive axes stay checkboxes (Add choices step and Compose; the catalogue decides, no name is hard-coded) | Compose swaps the pick and says so; Add Project asks a single-choice axis as a one-answer pick list | - (not built: record only) |
| Which version wins in `smith sync` | `smith sync --prefer highest\|lowest\|installed`, `--to name=version` | a dialog before the plan: installed (smith's pick), highest, lowest, cancel; then the plan and the confirmation (`--to` stays on the command line) | Sync Dependency Versions: the same three answers, the plan in a modal, `--yes` after a yes | - (not built: record only) |
| `new` and `convert` before a workspace exists | `smith new`, `smith convert [--level full --lint --test --build --ci] [--commit]` | the form collects the answers (a new convert form), convert shows its `--dry-run` plan, then `--yes` runs in a dialog that streams the output; success opens the workspace, failure brings the form back with its answers. `adopt` keeps its wizard | - (the extension runs `smith new --here` in a terminal; no convert form) | - |
| Findings that name a smith command carry a fix | `smith doctor --fix` | Doctor view runs the fix in place (review, then yes): Playwright pipeline, tauri CLI, golangci-lint, Rust and JDK pins with `smith ci generate`, architecture off. Remedies that are a command of another program (cargo, gradle, apt) stay text | the Fix row runs the same steps | - |
